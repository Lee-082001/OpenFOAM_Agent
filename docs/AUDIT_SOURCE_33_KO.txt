  ## 2. 잘 만든 부분—이 방향은 유지하는 게 좋아

  문제부터 많이 지적하겠지만, 기반 자체에는 좋은 선택이 많아.

  ### ① 물리 판단과 실행 검증을 분리하려는 설계

  LLM이 solver·mesh·수치 설정을 선택하고, Python이 출처·안전·파일·실행 근거를 검증하는 방향은 범용성에 적합해.

  새로운 문제마다 Python에 다음과 같은 분기를 늘리는 방식은 피하는 게 좋아.

  원통이면 이 solver
  열전달이면 이 template
  다상이면 저 dictionary

  지금 구조의 장점을 유지하면서 공통 검증 계약을 강화하는 게 맞아.

  ### ② 확정 intake와 case seal

  사용자가 확정한 문제 정의를 digest로 묶고, 최종 실행 입력을 seal로 검증하는 구조는 중요한 자산이야.

  다만 뒤에서 설명하듯, 파일 무결성과 물리적 타당성은 별도의 문제야. 둘을 분리해서 더 발전시키면 돼.

  ### ③ v3.6의 설계→파일 작성 분리

  큰 응답 하나에 설계·근거·파일을 전부 넣지 않고 나눈 건 좋은 개선이야.

  현재 문제는 분리 자체가 아니라 두 단계 사이에 무엇을 반드시 전달해야 하는지가 불완전한 것이야.

  ### ④ 설치 환경 기반 기능 탐색

  정적 capability graph에만 의존하지 않고 실제 설치된 실행 파일과 소스를 보는 방향도 좋아.

  다만 “소스에서 발견됨”과 “현재 환경에서 실제로 생성·실행 가능함”의 차이를 더 엄격하게 표현해야 해.

  ### ⑤ 실제 실패 로그를 같은 engineering agent에 반환

  오류 문자열을 보고 무조건 정해진 패치를 적용하기보다, 실제 실패 근거를 바탕으로 수리하는 구조는 범용 문제에서 필요해.

  이 구조를 유지하되 자동 수리가 바꿔도 되는 범위를 더 명확하게 해야 해.

  ## 3. 가장 먼저 고쳐야 할 실행·안전 문제

  ### 1) /solve 승인 검사가 일반 native 실행 경로에는 없다

  우선순위: 최상. 모의 검사로 재현.

  일반적인 runtime orchestrator에는 solve_approved 검사가 있어. 그런데 engineering의 RunNativeOpenFOAMAction은 그 경로를 거치지 않고 native command를 호출해.

  현재 이 분기는 대략 다음을 확인해.

  native 실행 활성화?
  파일 내용/문법 검사 통과?
  특정 mesh 도구의 선행 조건 충족?
  → 명령 실행

  여기에 **“지금 이 명령이 승인된 본 계산인가?”**가 빠져 있어.

  실제로 solve_approved=False, phase="prepare", role="utility"인 상태에서 foamRun을 전달했더니 모의 실행기까지 호출됐어.

  근거: /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/engineering/agent.py:3442, /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/schemas/engineering.py:368

  개선 방향

  명령의 권한을 LLM이 적어 준 role만으로 판단하면 안 돼.

  공통 실행 계층에서 다음을 검사해야 해.

  - 현재 workflow phase.
  - 실제 명령의 효과: 조회, 파일 생성, mesh 변경, 초기화, 본 계산, 삭제.
  - 해당 효과에 필요한 승인.
  - 승인된 execution spec과 case seal.
  - 실행 시간·CPU·메모리·디스크 예산.

  단순히 “solver처럼 생긴 명령은 전부 차단”하면 potentialFoam 같은 초기화 용도까지 불편해질 수 있어. 명령 이름뿐 아니라 사용 목적과 효과를 검증하는 구조가 필요해.

  완료 기준: prepare·repair·일반 native pipeline 어디에서 호출하든 승인 없는 본 계산은 프로세스 생성 전에 차단.

  ### 2) 자동 수리의 승인 범위가 plan.solver 문자열에 치우쳐 있다

  우선순위: 높음. 정적 분석.

  runtime repair에서 승인된 solver와 비교하는 부분은 다음 형태야.

  if plan.solver != approved_solver:
      ...

  그런데 이제 실행 구조는 단일 solver 문자열보다 훨씬 복잡해졌어.

  - driver.
  - solver module.
  - region별 module.
  - 실행 arguments.

  예를 들어 최상위 solver가 계속 foamMultiRun이면, 영역별 solver 배치가 달라져도 문자열 비교만으로는 그 차이를 잡지 못해.

  근거: /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/engineering/agent.py:1617, /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/engineering/agent.py:2306

  개선 방향

  승인 대상은 solver 이름이 아니라 실행 계약 전체여야 해.

  다만 모든 파일 수정마다 재승인을 요구할 필요는 없어. 변경을 구분하면 돼.

  - 문법 오류, solver 설정 오타: 허용된 자동 수리.
  - 물성·경계조건·영역 연결 변경: 물리 문제 변경 여부 검토.
  - driver·module·계산 규모의 큰 변경: 재승인.

  seal은 “현재 파일이 무엇인가”를 증명하고, approval은 “그 변경을 사용자가 어디까지 허용했는가”를 증명하도록 분리하는 게 좋아.

  다음처럼 같은 줄 안에 있으면 검사에서 빠졌어.

  근거: /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/tools/workspace.py:54, /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/tools/workspace.py:536

  개선 방향

  보안상 중요한 항목은 줄 기반 정규식보다 토큰/구문 구조를 기준으로 검사해야 해.

  특히 다음 형태를 같은 의미로 처리해야 해.

  - 여러 줄.
  - 인라인.
  - 중첩 dictionary.
  - 주석을 섞은 표현.

  ### 4) 안전 정책이 한편으로는 좁고, 다른 한편으로는 실행 효과를 충분히 제한하지 않는다

  우선순위: 높음. 구조적 문제.

  현재 허용 라이브러리 기본값은 네 개로 좁고, #include 계열은 내용 문자열에서 광범위하게 차단해.

  반면 trusted OpenFOAM 경로에서 발견한 실행 파일은 폭넓게 native 실행 대상으로 확장돼.

  이 조합은 다음 문제를 만들어.

  - 정상적인 복잡한 case 재사용은 막힐 수 있음.
  - 설치된 도구가 만드는 변경·삭제 효과는 충분히 구분되지 않음.

  “설치된 도구”와 “현재 단계에서 실행해도 되는 도구”는 다른 개념이야.

  근거: /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/tools/workspace.py:38, /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/tools/installation.py:78

  개선 방향

  안전 정책을 두 층으로 나누는 게 좋아.

  1. 문서/파일 정책: include 대상 경로, 해시, 순환 참조, 확장 크기, 신뢰된 라이브러리.
  2. 프로세스 정책: 명령 효과, 승인, 파일 접근, 자원 제한, 격리.

  include를 허용하려면 case 내부나 검증된 설치 자료만 안전하게 해석하고, 동적 코드 실행과 일반 파일 포함을 구분해야 해. 무조건 전부 허용하자는 뜻은 아니야.

  또한 shell=False와 경로 검사는 유용하지만, 그것만으로 OS 수준의 격리가 되는 건 아니야. 외부 사용자에게 서비스할 계획이라면 비특권 실행·호스트 읽기 제한·네트워크 정책도 필요해.

  ## 4. 범용 물리 문제를 막는 가장 큰 구조적 한계

  ### 6) multi-region은 실행 명세에 들어왔지만 pre-solve는 아직 단일 영역 중심이다

  우선순위: 높음. 재현.

  OpenFOAMExecutionSpec은 region별 solver를 표현할 수 있어.

  그런데 pre-solve는 항상 다음을 요구해.

  system/fvSchemes
  system/fvSolution
  constant/polyMesh/boundary

  그리고 0/ 아래의 필드들을 하나의 boundary 목록에 대조해.

  모의 다중 영역 fixture에 다음처럼 파일을 준비했는데도:

  system/fluid/fvSchemes
  system/solid/fvSchemes
  constant/fluid/polyMesh/boundary
  constant/solid/polyMesh/boundary
  0/fluid/T
  0/solid/T

  루트 파일이 없다는 이유로 실패했어.

  근거: /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/verification/presolve.py:18, /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/verification/presolve.py:98

  개선 방향

  RegionCaseLayout 같은 공통 표현이 필요해.

  각 region마다:

  - mesh 위치.
  - 필드 위치.
  - dictionary 위치.
  - solver module.
  - 필수 필드.
  - patch 목록.
  - 다른 region과 연결된 interface.

  를 정의하고, authoring·pre-solve·mesh evidence·runtime·post-processing이 모두 같은 정보를 사용해야 해.

  여기에 루트 dummy 파일을 추가해 검사를 통과시키는 식으로 해결하면 안 돼. 검사기의 영역 모델을 바로잡아야 해.

  quantity / value / unit / dimensions
  region / patch / material / time dependence
  source / active status / reference definition

  ## 8. “실행 성공”과 “요청한 계산을 제대로 수행함”의 구분

  ### 21) 현재 runtime 완료 판정은 너무 약하다

  우선순위: 높음. 재현.

  현재 parser는 대체로 다음을 본다.

  - return code 0.
  - End 존재.
  - Time 기록 존재.
  - fatal/non-finite 오류 없음.

  그래서:

  Time = 0
  End

  만 있어도 success=True, completed=True가 됐어.

  근거: /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/tools/parsers.py:32

  이 함수에는 목표 종료 시간이나 초기 시간 같은 계약이 전달되지 않으니, 요청한 시간 구간을 계산했는지 알 수 없어.

  개선 방향

  성공을 한 단계가 아니라 여러 단계로 표현하면 좋아.

  프로세스 정상 종료
  → 의도한 계산 진행
  → 종료 조건 충족
  → 결과 파일 존재/유한성 확인
  → 수치 품질 확인
  → 물리 목표 확인

  비정상 계산은 시간 구간을, 정상 계산은 적절한 수렴/종료 조건을 확인해야 해. 모든 문제에 동일한 endTime 판정을 강제하면 또 다른 범용성 문제가 생겨.

  특히 “vortex shedding을 보고 싶다”는 요청에서는 solver 종료와 shedding 관측을 구분해야 해.

  ### 22) timeout이 실행 결과로 정리되지 않는 경로가 있다

  우선순위: 중상. 정적 분석.

  streaming runner는 timeout에서 process를 kill하고 TimeoutExpired를 발생시켜.

  이 경우 정상 ToolResult와 같은 방식으로 부분 로그·종료 원인·복구 가능성을 넘기는 경로가 약해져.

  또 runtime policy는 최대 86,400초를 허용하지만 runner 기본 상한은 3,600초야.

  근거: /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/tools/safe_runner.py:94, /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/tools/safe_runner.py:332, /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/schemas/
  simulation.py:31

  개선 방향

  timeout을 “알 수 없는 Python 예외”가 아니라 구조화된 실행 결과로 반환해야 해.

  - 종료 이유.
  - 부분 로그 위치.
  - 마지막 계산 시간.
  - 남아 있는 process 여부.
  - restart 가능한 결과 존재 여부.
  - 재시도해도 되는지.

  명령 전체 process group을 관리하는 구조도 병렬 실행 전에 필요해.

  ### 23) 긴 계산의 로그 메모리 사용이 커질 수 있다

  우선순위: 중상. 정적 분석.

  streaming runner는 출력 queue와 chunks를 메모리에 축적하고, 최종 문자열을 만들어 parser에 전달해. parser도 줄 목록과 residual 목록을 만든다.

  긴 계산에서는 로그 크기가 곧 agent 메모리 부담이 될 수 있어.

  근거: /home/mlfm/OpenFOAM_Agent/src/openfoam_agent/tools/safe_runner.py:352

  개선 방향

  - 로그 원문은 디스크에 streaming 저장.
  - 메모리는 bounded tail만 유지.
  - residual/시간/Courant는 증분 parser로 처리.
  - 원본 로그 hash를 증분 계산.
  - 상세 시계열은 별도 artifact.
  - 출력 과다·디스크 부족도 명시적 중단 사유로 처리.

  이건 성능 최적화이기도 하지만, 대형 case를 안정적으로 돌리기 위한 기본 기능이야.

  ### 24) post-processing 실행도 새 execution 구조를 따라가지 못한다

  개선 방향

  post-processing도 다음을 명시적으로 받아야 해.

  - 대상 region.
  - 해당 region의 solver module.
  - 필요한 field와 물성 context.

  ## 11. 내가 추천하는 개발 순서

  한 번에 전부 고치기보다 다음 순서가 좋아.

  ### 1단계: 현재 약속을 확실히 지키기

  가장 먼저 할 것:

  1. 모든 native 실행 경로의 승인 검사 통합.
  2. libs 구문 검사 수정.
  3. --solve, /feedback 상태 전이 수정.
  4. 실제 subprocess 기반 예산 집계.
  5. 숫자 override 처리.
  6. Codex 인증 종류 검사.
  7. 위 항목 회귀 테스트.

  새 물리 기능을 늘리지 않아도 안정성이 크게 올라가는 작업들이야.

  ### 2단계: 공통 계약을 끝까지 연결하기

  그다음:

  1. region-aware case layout.
  2. 영역별 mesh evidence와 무효화.
  3. 실행 계약 전체에 대한 승인·수리 정책.
  4. authoring evidence pack.
  5. 필수 조건을 자르지 않는 context compiler.
  6. checkpoint/resume.

  이 단계가 범용성의 핵심이라고 봐.

  ### 3단계: 현실적인 사용 범위 넓히기

  그다음에:

  1. 실제 geometry/데이터 가져오기.
  2. 기존 case 수정·restart.
  3. 로컬 MPI.
  4. 일반화된 정량 목표와 검증.
  5. 버전별 native 통합 평가.

  이 순서면 기능을 추가할수록 기존 구조가 흔들리는 현상을 줄일 수 있어.

  ## 최종 평가

  현재 프로젝트를 나는 이렇게 평가해.

  > 범용 CFD 에이전트를 지향하는 설계는 상당히 구체화됐다. 다만 일부 공통 계층이 여전히 단일 영역·단일 solver·짧은 실행·단순한 요구사항을 전제로 하고 있어, 새로 늘어난 표현 범위를 끝까지 받쳐주지는 못한다.

  그래서 다음 버전의 핵심 목표는 “더 많은 OpenFOAM 기능을 알게 하기”보다 다음이었으면 해.

  “어떤 문제를 선택하든, 사용자 조건·영역 구조·실행 권한·검증 근거가 intake부터 결과까지 일관되게 유지되게 하기.”

  그 기반을 만들면 새로운 solver나 물리 모델은 비교적 자연스럽게 붙을 거야. 반대로 그 기반 없이 capability 수만 늘리면, 모델이 선택할 수 있는 것은 많아져도 끝까지 성공시키는 비율은 잘 올라가지 않을 가능성이
